Don't start
with an agent.

Start with the job. Add autonomy only when the problem demands it.

Prompted chat is the floor under every choice. It is not the job, and it is not a rung you climb.

Business
problem

1. Choose the right pattern

Select the problem. The recommendation says why, and when to move up.

What does the system need to do?

Select the problem that best matches the job. Most jobs stop before an agent.

Recommendation

Start with retrieval.

Ground the answer in the docs and cite it. If that is the job, stop.

Move up when the job must read or write a live system, or when the path can no longer be written down in advance.

2. Watch the system work

Checks, a retry, and a human gate.

Agentic AI is a loop, not a menu. A known sequence never enters it.

User request The job, in one sentence.
Observe Read the context and what the tools may do.
Decide Choose the tool and name the stop.
Act Call the tool, then do the task.
Verify Check the output and the errors.
Needs approval? Money, production, and irreversible writes wait.
Success Deliver the result and keep the trace. If approval does not come, stop.

Retry / continue If it fails, try again or escalate. The loop has to be able to stop.

3. Choose the architecture

Different jobs, not a vendor menu.

RAG

Best when the answer has to come from trusted knowledge, with a citation.

No memory of its own Workflow

Best when the sequence is known. Code owns the order. The model fills a slot.

Deterministic path Agent

Best when the work branches, retries, and must be able to stop. State is the point.

Stateful loop Tools / MCP

Best when the loop must reach a live system. A schema and a permission, not a second copy of the docs.

Named tools Rules / skills

Rules are standing orders. A skill is a runbook you load when the task matches.

Behavior, not a layer Evaluation

Golden cases before you ship, and again after a meaningful change.

Before and after

A2A only when another team owns the next agent. Otherwise stay inside one loop. Skills stay runbooks. A person still approves money, production, and irreversible writes.

4. Build safely

From the first day, not after the demo.

Security boundariesData, identity, network, and what the loop may not touch.
Tool permissionsLeast privilege. An allowlist, not a blank key.
Budgets and limitsStep cap, spend cap, and a way to turn the loop off.
TraceabilityLogs, lineage, and the tool path when a case fails.
EvaluationBefore release, after a meaningful change, and while it runs.
Human gateRisk-based. If approval does not come, the loop stops.

5. Prove it works

Name the bars. Do not invent them.

  • Task successThe share of jobs that finished the real task.
  • Factual accuracyCited answers against the source, not a vibe.
  • Escalation rateHow often a person has to take the job back.
  • LatencyThe slow tail, not the demo.
  • Cost per taskSpend for one finished job, including retries.
  • Failure recoveryA failed tool call that stops cleanly, or tries once and stops.

An outcome names the effort it replaced, the accuracy bar, and the cost. Without those three, you have activity.
