## The question

When three different agents touch the same repo in one evening, how do you know **what was decided, what ran, and what still needs a human**?

## The problem with "just use the IDE"

Cursor (and similar tools) are excellent at **local, single-threaded** work. They are weaker as a **system**:

- No durable ledger of plans vs outcomes across sessions.
- No first-class "this child agent owns tests, that one owns docs."
- No explicit **Debug** phase when verification fails — you improvise in chat.

ProjectHelm (JARVIS) is my attempt at a **thin control plane** on my machine: not another chat UI, but state + orchestration around the Cursor SDK.

## What ProjectHelm actually does

At a high level:

1. **Plan** — break a goal into scoped steps with owners and done criteria.
2. **Agent** — dispatch work to child agents with bounded context.
3. **Debug** — when checks fail, loop with evidence instead of guessing.
4. **Ledger** — append events so I can answer "what happened after the refactor prompt?"

The dashboard is FastAPI + a small web UI. The interesting part is not the framework — it is the **contract**: every loop produces artifacts a human can audit.

## Design choices I’m keeping

- **Local-first** — no cloud orchestrator billing per agent hour.
- **Explicit phases** — Plan / Agent / Debug are named, not implied by prompt tone.
- **Event ledger** — if it is not in the ledger, it did not happen for the project.
- **Human kill switch** — I can stop a run without guessing which subprocess to kill.

## What I’m not solving yet

- Multi-user teams or permissions — this is a personal workshop tool.
- Fully autonomous shipping — merge buttons stay with me.
- Replacing Cursor — ProjectHelm coordinates; the IDE still edits.

## Takeaway

Agents become useful at scale when you treat them like **workers with a foreman**, not like a single omniscient chat. Build the foreman layer first: state, phases, and a log you can read on Monday morning.
